## 0. 两条不能碰的红线

在讨论任何技术细节之前，先把课件里两条会直接吃掉分数的规则摆出来，整个方案都是围绕它们设计的。

**红线一：后台逻辑不能用脚本语言。**

> 开发语言选择：C/C++/C#/Java/Go；用户界面可以采用脚本语言编写；**但若后台逻辑也选择脚本语言，则小组基础分记 10 分。**

基础分满分 40。如果备份/还原逻辑写在 Python 里，直接掉到 10 分，后面所有扩展做得再好也补不回来。

**结论：所有备份、还原、元数据、压缩、加密逻辑必须在 C++ 里。Python 只允许出现在 GUI 层，而且 GUI 层不得包含任何业务判断——它只负责收集参数、启动进程、渲染进度。**

**红线二：扩展功能不能"直接"用第三方库实现。**

> 库的使用：对所有扩展功能，如使用第三方库/程序/代码"直接"实现，对应功能扩展分总分记为原来的 50%。

即：压缩不能调 zlib/miniz，加密不能调 OpenSSL/CryptoAPI，打包不能调 libarchive。这三块必须手写算法。

需要区分"直接实现功能"和"工程基础设施"：

| 用途 | 判定 | 说明 |
|---|---|---|
| zlib / miniz 做压缩 | 扣分 | 压缩功能本身被第三方替代了 |
| OpenSSL 做 AES | 扣分 | 同上 |
| GoogleTest 做单测 | 不扣 | 评分表反而鼓励"使用第三方测试工具" |
| PySide6 做界面 | 不扣 | GUI 用脚本语言是课件明确允许的 |
| Win32 API 读 ACL | 不扣 | 操作系统 API，不是第三方库 |
| nlohmann/json 输出进度 | 不扣（但建议自己写） | 属于 I/O 格式，非评分功能；不过我们的 JSON 输出很简单，自己写 200 行更保险 |

**保守做法：核心库零第三方依赖，只依赖 Windows SDK 和 C++17 标准库。** 第三方依赖只出现在 `tests/` 和 `gui/` 目录。

## 2. 总体架构

### 2.1 分层

```
┌──────────────────────────────────────────────┐
│  gui/          Python + PySide6              │  队友 B
│  只做：参数收集、进程启动、进度渲染、结果展示      │
└───────────────┬──────────────────────────────┘
                │  subprocess + argv + stdin(密码) + stdout(JSON)
┌───────────────▼──────────────────────────────┐
│  cli/          cbk.exe                       │  我
│  参数解析 · JSON 事件上报 · 退出码             │
└───────────────┬──────────────────────────────┘
┌───────────────▼──────────────────────────────┐
│  core/         libcbk (静态库)                │
│  ┌────────────────────────────────────────┐  │
│  │ BackupEngine / RestoreEngine  编排      │  │  我
│  ├────────────────────────────────────────┤  │
│  │ Scanner     目录遍历 · 类型识别 · 硬链接去重 │  我
│  │ Metadata    属性/时间戳/SID/DACL 读写     │  我
│  ├────────────────────────────────────────┤  │
│  │ IPacker     条目如何序列化              │  │  队友 A（打包解包）
│  │ IStage      字节流变换（可串联）          │  │  队友 A（压缩）/ B（加密）
│  ├────────────────────────────────────────┤  │
│  │ ArchiveWriter / ArchiveReader  容器读写  │  │  我（提供框架）
│  ├────────────────────────────────────────┤  │
│  │ platform_win  Win32 薄封装 · 特权提升    │  │  我
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

**关键点：我负责的是"骨架 + 两块肉"，队友只需要实现接口，不需要改我的文件。** 这是分工能并行的前提，也是避免最后一周互相等待的关键。

### 2.2 数据流

备份方向：

```
目录树
  → Scanner 逐条产出 EntryMeta（含类型、元数据、SDDL）
  → BackupEngine 决定这条要不要读内容（目录/链接/硬链接引用 不读）
  → IPacker 把 EntryMeta + 内容序列化成字节流
  → IStage 链 依次变换（压缩 → 加密）
  → ArchiveWriter 落盘到 .cbk
```

还原方向就是完全镜像的逆过程，注意 Stage 链要**逆序**执行（解密 → 解压）。

## 3. `.cbk` 容器格式

这是整个项目最重要的一份契约——所有人都要按它读写。**一旦冻结，改动必须走组内评审并升 `formatVersion`。**

### 3.1 整体布局

```
 offset 0
 ┌────────────────────────────────┐
 │  FileHeader        固定 128 字节 │  明文，永不加密
 ├────────────────────────────────┤
 │  PipelineDesc      变长          │  明文，描述用了哪些算法
 ├────────────────────────────────┤
 │                                │
 │  Data Region                   │  经过 Packer + Stage 链处理
 │  （所有条目的元数据与内容）        │
 │                                │
 ├────────────────────────────────┤
 │  Index Region                  │  条目索引表，同样经过 Stage 链
 ├────────────────────────────────┤
 │  Footer            固定 64 字节  │  明文，整体校验和
 └────────────────────────────────┘
```

**为什么头部和 PipelineDesc 必须明文**：还原时要先知道"这个包用了什么压缩算法、什么加密算法"，才能组装出正确的 Stage 链。如果这段也加密了就成了死锁。这也意味着加密只保护数据，不保护"用了哪种加密"这个事实——这是所有加密归档格式的通行做法。

**为什么 Index 单独放在尾部而不是头部**：备份时是流式写入的，写完最后一个文件才知道每个条目的 `storedSize` 和偏移。放尾部就不需要回头 seek 改写。还原时先读 Footer 拿到 Index 偏移，跳过去读索引，再按需读数据。

### 3.2 FileHeader（128 字节，小端序）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `magic` | ASCII `"CBKF"` |
| 4 | 2 | `formatVersion` | 当前 `1` |
| 6 | 2 | `flags` | bit0 已打包 / bit1 已压缩 / bit2 已加密 |
| 8 | 4 | `headerSize` | = 128 |
| 12 | 4 | `pipelineDescLen` | PipelineDesc 字节长度 |
| 16 | 8 | `createdAt` | FILETIME（100ns since 1601-01-01 UTC） |
| 24 | 8 | `entryCount` | 条目总数 |
| 32 | 8 | `dataOffset` | Data Region 起始偏移 |
| 40 | 8 | `dataSize` | Data Region 字节数（处理后） |
| 48 | 8 | `indexOffset` | Index Region 起始偏移 |
| 56 | 8 | `indexSize` | Index Region 字节数（处理后） |
| 64 | 8 | `totalOriginalBytes` | 原始数据总量，用于算压缩率 |
| 72 | 2 | `sourceRootLen` | 源根路径 UTF-8 长度 |
| 74 | 54 | `reserved` | 全 0，给后续扩展留 |

`reserved` 留 54 字节不是浪费——网络备份的增量链 ID、卷影副本时间点这类字段将来要往这里放，不至于破坏兼容性。

### 3.3 PipelineDesc

一行 ASCII，冒号分隔，描述 Data/Index Region 经过的处理链，**顺序即写入时的应用顺序**：

```
packer=tar;stages=lz77,huffman,aes128-cbc
packer=cbk-native;stages=
```

还原时按这个字符串反向构造 Stage 链。新增算法只需要在这里加一个新名字并注册工厂，不用改格式版本。

### 3.4 EntryMeta（条目元数据）

这是我负责产出、队友负责序列化的结构体。字段设计直接对应"文件类型"和"元数据"两项评分。

```cpp
enum class FileType : uint8_t {
    Regular      = 0,  // 普通文件
    Directory    = 1,  // 目录
    SymlinkFile  = 2,  // 文件符号链接
    SymlinkDir   = 3,  // 目录符号链接
    Junction     = 4,  // 目录联接（mount point）
    HardlinkRef  = 5,  // 硬链接，指向已存条目，不存内容
    Unsupported  = 6,  // 其他重解析点/设备，仅记录不还原
};

struct EntryMeta {
    uint64_t     id;               // 条目序号，从 0 递增
    std::wstring relativePath;     // 相对源根，'\' 分隔，落盘转 UTF-8
    FileType     type;

    // —— 元数据（评分项：属主/时间/权限）——
    uint32_t     attributes;       // FILE_ATTRIBUTE_* 位掩码
    uint64_t     creationTime;     // FILETIME
    uint64_t     lastAccessTime;   // FILETIME
    uint64_t     lastWriteTime;    // FILETIME
    std::string  sddl;             // 安全描述符（SDDL 字符串，含 O:/G:/D:）

    // —— 内容 ——
    uint64_t     originalSize;     // 原始字节数，目录/链接为 0
    uint64_t     storedSize;       // 处理后字节数（Packer/Stage 填写）
    uint64_t     dataOffset;       // 在 Data Region 内的偏移
    uint32_t     crc32;            // 原始内容校验和

    // —— 类型相关 ——
    std::wstring linkTarget;       // 符号链接/junction 的原始目标（可能是相对路径）
    uint32_t     reparseTag;       // 重解析点标签，Unsupported 时用于诊断
    uint64_t     hardlinkRefId;    // HardlinkRef 指向的条目 id
};
```

**几个设计理由：**

- `sddl` 存字符串而不是二进制安全描述符。SDDL 是文本、可读、可 diff，写测试用例和答辩演示时能直接肉眼验证；`ConvertSecurityDescriptorToStringSecurityDescriptorW` / `ConvertStringSecurityDescriptorToSecurityDescriptorW` 两个 API 无损互转。体积代价可以忽略（典型 SDDL 200~400 字节，且会被压缩掉）。
- 时间戳存 `FILETIME` 原值（100ns 精度）而不是 `time_t`（秒）。用 `time_t` 会丢精度，还原后时间戳跟原文件对不上，测试用例会挂。
- `linkTarget` 存**原始**目标而不是解析后的绝对路径。符号链接的语义就是"存一个字符串"，解析后再存就把相对链接变成了绝对链接，还原到别的机器上就废了。
- 硬链接不复制内容，只存一个 `hardlinkRefId`。这既省空间，也是"正确处理硬链接"这个评分点的核心——如果把 3 个硬链接当成 3 个独立文件存，还原后它们就不再是同一个实体了。

### 3.5 Footer（64 字节，明文）

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | `magic` = `"CBKE"` |
| 4 | 8 | `indexOffset`（与 Header 冗余，用于头部损坏时抢救） |
| 12 | 4 | `headerCrc32` |
| 16 | 4 | `indexCrc32` |
| 20 | 4 | `dataCrc32` |
| 24 | 40 | `reserved` |

`cbk verify` 命令就靠这三个 CRC 工作。

## 4. 给扩展功能留的两个接口

这是本方案的核心设计——**队友只需要写实现类并注册，一行都不用改我的代码**。

### 4.1 `IPacker` —— 条目怎么序列化（打包解包，每种算法 10 分）

```cpp
// core/include/cbk/packer.h
class ISink {
public:
    virtual ~ISink() = default;
    virtual void write(const uint8_t* data, size_t len) = 0;
};

class IPacker {
public:
    virtual ~IPacker() = default;
    virtual std::string name() const = 0;          // "tar" / "cpio" / "cbk-native"

    // —— 打包 ——
    virtual void beginEntry(const EntryMeta& meta, ISink& out) = 0;
    virtual void writeData(const uint8_t* data, size_t len, ISink& out) = 0;
    virtual void endEntry(ISink& out) = 0;
    virtual void finish(ISink& out) = 0;           // 写结束标记（如 tar 的两个空块）

    // —— 解包 ——
    // 从 src 顺序读，每解析出一个条目就回调 onEntry；内容通过 onData 分块吐出
    virtual void unpack(ISource& src,
                        const std::function<void(const EntryMeta&)>& onEntry,
                        const std::function<void(const uint8_t*, size_t)>& onData) = 0;
};
```

**评分表说"每种算法 10 分"，所以队友 A 至少要实现两种才能拿满：**

- `TarPacker` —— POSIX ustar 格式，512 字节块对齐，头部含 checksum。经典、有标准可查、能用 7-Zip 打开验证（很利于演示）。Windows 特有的 SDDL/属性位放进 PAX 扩展头或 GNU 长名扩展。
- `CpioPacker` —— SVR4 newc 格式，无 512 对齐，头部是 ASCII 十六进制。跟 tar 形成对照，答辩时可以讲"两种打包格式的空间开销对比"。

我负责实现兜底的 `NativePacker`：`[EntryMeta 长度前缀 TLV][内容原样]`，最简单，用于基础部分单独跑通和作为其他 packer 的正确性对照基准。

### 4.2 `IStage` —— 字节流怎么变换（压缩 10 分/种、加密 10 分/种）

```cpp
// core/include/cbk/stage.h
class IStage {
public:
    virtual ~IStage() = default;
    virtual std::string name() const = 0;   // "huffman" / "lz77" / "aes128-cbc" / "xor"

    // 处理一块输入，产出的字节写进 out。允许内部缓冲，不要求 1:1。
    virtual void process(const uint8_t* data, size_t len, ISink& out) = 0;
    // 冲刷内部缓冲，写出尾部（如 Huffman 的位对齐填充、CBC 的 PKCS#7 padding）
    virtual void finish(ISink& out) = 0;

    // 可选：需要密码的 Stage 从这里拿
    virtual void setPassword(const std::string& pwd) {}
};

// 每个 Stage 都要有配对的逆变换
class IStageFactory {
public:
    virtual std::unique_ptr<IStage> createForward() = 0;   // 压缩 / 加密
    virtual std::unique_ptr<IStage> createInverse() = 0;   // 解压 / 解密
};
```

Stage 可以任意串联，`BackupEngine` 按 PipelineDesc 顺序 `process`，`RestoreEngine` 按**逆序**调用 `createInverse()`。

建议实现：

| 类型 | 算法 | 备注 |
|---|---|---|
| 压缩 | Huffman 编码 | 必须自己写码表构建和位流读写；码表要序列化进输出 |
| 压缩 | LZ77 / LZSS | 滑动窗口，跟 Huffman 组合起来就接近 Deflate，答辩有讲头 |
| 加密 | XOR / 维吉尼亚 | 简单，用来先把管线跑通 |
| 加密 | AES-128-CBC | 手写 S 盒、密钥扩展、CBC 模式；IV 随机生成并存进 Stage 输出头部 |

密钥派生建议手写 PBKDF2-HMAC-SHA256（迭代 10000 次），不要把用户密码直接当密钥用——答辩时这是个明确的加分点。

### 4.3 顺序必须是「打包 → 压缩 → 加密」

这条要在文档和代码里都写死，不能让人配错：

- **压缩必须在加密之前。** 加密输出是高熵伪随机数据，压缩率会退化到 0 甚至为负（还多出码表开销）。反过来先压再加，压缩率正常。
- **打包必须在最外层。** 打包决定的是"条目边界在哪"，是结构层；压缩/加密是字节层。结构层在内、字节层在外，解包时才能先解密解压还原出完整字节流，再按结构解析。

`PipelineDesc` 的解析器要校验这个顺序，配错直接报参数错误退出（退出码 3），而不是产出一个能生成但还原不了的包。

## 5. CLI 契约（给 GUI 队友的接口）

### 5.1 命令

```
cbk backup  --source <目录> --dest <文件.cbk>
            [--packer <name>] [--compress <name>] [--encrypt <name>]
            [--password-stdin] [--follow-symlinks] [--progress json]

cbk restore --archive <文件.cbk> --dest <目录>
            [--password-stdin] [--overwrite skip|force|rename]
            [--no-metadata] [--progress json]

cbk list    --archive <文件.cbk> [--json] [--password-stdin]

cbk verify  --archive <文件.cbk>

cbk info                                # 输出支持的 packer/stage 列表，GUI 用它动态填下拉框
```

`cbk info` 这一条很关键：GUI 不硬编码算法名，而是启动时问一次核心支持哪些算法。队友 A 新加一个压缩算法，GUI 一行不用改就多出一个选项。

### 5.2 密码走 stdin，不走命令行参数

命令行参数在 Windows 上可以被任意进程通过 `NtQueryInformationProcess` 读到，也会进 GUI 的日志。所以 `--password-stdin` 表示"从标准输入读一行作为密码"，Python 侧：

```python
proc = subprocess.Popen([...,"--password-stdin"], stdin=PIPE, stdout=PIPE, text=True, encoding="utf-8")
proc.stdin.write(password + "\n")
proc.stdin.flush()
```

这条写进设计文档里，答辩时属于"安全性考虑"的加分项。

### 5.3 进度上报：stdout 逐行 JSON

每行一个完整 JSON 对象，`\n` 结尾，**每行写完立刻 flush**（否则 GUI 进度条会卡住不动然后一次跳完）。

```json
{"type":"start","op":"backup","total":4567,"totalBytes":1234567890}
{"type":"progress","done":123,"bytes":45678901,"current":"src\\main.cpp"}
{"type":"warn","path":"C:\\x\\y.dat","code":"E_SHARING_VIOLATION","msg":"文件被占用，已跳过"}
{"type":"warn","path":"C:\\x\\link","code":"E_SYMLINK_PRIVILEGE","msg":"无权创建符号链接，已降级为普通文件"}
{"type":"result","status":"partial","entries":4566,"skipped":1,"bytes":1234567890,"elapsedMs":8421,"outputBytes":456789012}
```

`current` 字段建议每 100ms 最多发一次（在 Engine 里限流），否则备份小文件多的目录时 stdout 会被进度刷爆，反而拖慢整体速度。

**stderr 只用于崩溃堆栈和致命错误**，不混进 JSON 流。

### 5.4 退出码

| 码 | 含义 | GUI 应有的表现 |
|---|---|---|
| 0 | 全部成功 | 绿色"完成" |
| 1 | 部分成功（有 warn，但包是完整可用的） | 黄色"完成，N 项被跳过"，可点开看详情 |
| 2 | 失败（包未生成或已损坏） | 红色"失败" |
| 3 | 参数错误 | 红色，且这属于 GUI 自己的 bug |

## 6. 我负责的三块——详细设计

### 6.1 基础备份还原

#### 遍历

用 `FindFirstFileW` / `FindNextFileW` 而不是 `std::filesystem::recursive_directory_iterator`。原因：`WIN32_FIND_DATAW` 一次就把 `dwFileAttributes`、三个时间戳、文件大小全给了，而且当 `FILE_ATTRIBUTE_REPARSE_POINT` 置位时 `dwReserved0` 直接是重解析点标签——不用为每个文件单独 `CreateFile` + `DeviceIoControl` 去问。对几万个文件的目录树，这个差别是数量级的。

**显式用迭代 + 自己的栈，不用递归**。深目录会爆栈，而且迭代版本更容易做"暂停/取消"。

#### 长路径

Windows 默认 `MAX_PATH` = 260。备份软件几乎必然会遇到超长路径。所有传给 Win32 API 的路径统一加 `\\?\` 前缀：

```cpp
// C:\a\b  ->  \\?\C:\a\b
// \\srv\share\a  ->  \\?\UNC\srv\share\a
std::wstring ToExtendedPath(const std::wstring& path);
```

注意 `\\?\` 路径不做任何规范化，所以传进去之前必须先自己转成绝对路径、去掉 `.` 和 `..`、把 `/` 换成 `\`。这是一个很容易漏、漏了就在深目录上莫名其妙失败的点，**要有专门的单元测试**。

#### 文件读写

- 打开：`CreateFileW(path, GENERIC_READ, FILE_SHARE_READ|FILE_SHARE_WRITE|FILE_SHARE_DELETE, ..., FILE_FLAG_BACKUP_SEMANTICS|FILE_FLAG_SEQUENTIAL_SCAN, ...)`
  - 三个 SHARE 位全开：否则别人正在写的文件根本打不开
  - `FILE_FLAG_BACKUP_SEMANTICS`：**必须有**。它有两个作用——允许打开目录句柄（设目录时间戳时要用），以及配合 `SeBackupPrivilege` 绕过 ACL 读取无权访问的文件
  - `FILE_FLAG_SEQUENTIAL_SCAN`：提示缓存管理器做预读
- 固定 64 KB 缓冲流式读写，**任何情况下不整文件读进内存**
- 打不开的文件：发 `warn` 事件，跳过，最终退出码 1，不中断整个备份

#### 特权提升

进程启动时尝试启用三个特权：

```cpp
EnablePrivilege(SE_BACKUP_NAME);    // 绕过 ACL 读
EnablePrivilege(SE_RESTORE_NAME);   // 绕过 ACL 写、设置任意属主
EnablePrivilege(SE_SECURITY_NAME);  // 读写 SACL
```

流程是 `OpenProcessToken` → `LookupPrivilegeValue` → `AdjustTokenPrivileges`。

**注意 `AdjustTokenPrivileges` 即使部分失败也返回 TRUE**，必须再查 `GetLastError() == ERROR_NOT_ALL_ASSIGNED` 才知道到底成没成。这是个经典坑。

拿不到特权（非管理员运行）不是致命错误——降级运行，只是遇到无权访问的文件时会跳过并 warn。GUI 侧可以检测到这种情况并提示"以管理员身份重启可备份更多文件"。

#### 还原的顺序问题

还原不能简单地按索引顺序一路建过去，有三个顺序陷阱：

1. **目录时间戳必须后序设置。** 先建目录 → 填内容 → **最后**才设目录的时间戳。因为往目录里写文件会更新目录的 `lastWriteTime`。如果建完目录立刻设时间戳，写完子文件就被覆盖了。
2. **只读属性必须最后设。** 如果先给文件设了 `FILE_ATTRIBUTE_READONLY`，后续设时间戳和 ACL 会失败。正确顺序：写内容 → 设时间戳 → 设 ACL → **最后**设属性位。
3. **硬链接必须在目标条目还原之后建。** 由于 `hardlinkRefId` 一定指向更小的 id，按 id 升序还原就自然满足。但如果将来做并行还原，这个约束要显式检查。

所以 `RestoreEngine` 分三趟：

```
Pass 1: 建所有目录（不设元数据）
Pass 2: 按 id 升序还原文件内容、符号链接、junction、硬链接；每个文件立即设自己的元数据
Pass 3: 逆序遍历目录列表，设置目录的时间戳、ACL、属性位
```

Pass 3 逆序是为了从最深的目录往外设，避免设置父目录时间戳后又去动子目录。

### 6.2 文件类型支持

#### Windows 上"管道/链接/设备"对应什么

评分要求原文是 Linux 语境的。要在设计文档里专门写一节做平台映射分析——这本身就是"内容完整"的加分点：

| Linux 概念 | Windows 对应物 | 是否会出现在目录树 | 我们的处理 |
|---|---|---|---|
| 符号链接 `symlink` | 符号链接（重解析点，tag `IO_REPARSE_TAG_SYMLINK`） | 是 | 完整备份还原，区分文件/目录两种 |
| 硬链接 `hard link` | 硬链接（同一 MFT 记录多个目录项） | 是 | 检测并去重，还原时用 `CreateHardLinkW` |
| 挂载点 `mount point` | 目录联接 Junction（tag `IO_REPARSE_TAG_MOUNT_POINT`） | 是 | 完整备份还原 |
| 命名管道 `FIFO` | 命名管道，位于 `\\.\pipe\` 命名空间 | **否** | 不在文件系统目录树中，无法也无需备份；文档中说明 |
| 设备文件 `/dev/*` | 设备对象，位于 `\\.\` 命名空间 | **否** | 同上 |
| —— | 其他重解析点（OneDrive 占位符、AppExecLink 等） | 是 | 识别为 `Unsupported`，记录 `reparseTag` 并 warn，不递归进去 |

**这张表是"文件类型支持"这一项的答辩底稿**：不是"Windows 没有所以我们不做"，而是"我们分析了每一种，说明了为什么某些在本平台不适用，并对本平台特有的类型做了完整处理"。

#### 符号链接与 Junction

判定：

```cpp
bool isReparse = (attrs & FILE_ATTRIBUTE_REPARSE_POINT) != 0;
// FindFirstFileW 场景下，tag 直接在 findData.dwReserved0
// 单独查询则用 GetFileAttributesExW + DeviceIoControl
```

读目标：`DeviceIoControl(h, FSCTL_GET_REPARSE_POINT, ...)` 拿 `REPARSE_DATA_BUFFER`。

- `SymbolicLinkReparseBuffer` 里有 `SubstituteName` 和 `PrintName`，还有 `Flags`（`SYMLINK_FLAG_RELATIVE` 表示相对链接）。**存 `PrintName`**（用户可见形式），并把 relative 标志一起记下来。
- `MountPointReparseBuffer` 只有 `SubstituteName`（形如 `\??\C:\target`），要剥掉 `\??\` 前缀。

**不要用 `GetFinalPathNameByHandle`**——那会把链接解析成最终目标，正好丢掉我们要备份的信息。

创建：

- 符号链接：`CreateSymbolicLinkW(link, target, flags)`。`flags` 要按目标是文件还是目录设 `SYMBOLIC_LINK_FLAG_DIRECTORY`，并且**总是或上 `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE`（0x2）**——在开了开发者模式的 Win10/11 上这能免管理员创建；在老系统上这个标志会导致 `ERROR_INVALID_PARAMETER`，所以要**失败后不带该标志重试一次**。
  - 两次都失败（`ERROR_PRIVILEGE_NOT_HELD`）：发 warn，降级——目录链接建成空目录，文件链接建成 0 字节文件，并在报告里列出。不能因为一个链接建不了就中断整个还原。
- Junction：先 `CreateDirectoryW`，再打开目录句柄，`DeviceIoControl(FSCTL_SET_REPARSE_POINT, ...)` 写入自己构造的 `REPARSE_DATA_BUFFER`。**不需要管理员权限**，这是 junction 比符号链接方便的地方。

**默认不跟随链接**（`--follow-symlinks` 才跟随）。默认跟随会导致：备份体积暴涨、指向外部的链接把不该备份的东西拖进来、循环链接直接死循环。跟随模式下必须维护一个 `(volumeSerial, fileIndex)` 的已访问集合来断环。

#### 硬链接去重

对每个 `nNumberOfLinks > 1` 的普通文件（这个字段来自 `GetFileInformationByHandle`），用 `(dwVolumeSerialNumber, nFileIndexHigh, nFileIndexLow)` 作为唯一键查表：

- 首次遇到：正常存内容，把 `key -> entryId` 记进 map
- 再次遇到：类型标为 `HardlinkRef`，`hardlinkRefId` = 表里的 id，**不存内容**

只对 `nNumberOfLinks > 1` 的文件查表，避免给几万个普通文件白建哈希表项。

还原时 `CreateHardLinkW(newPath, existingPath, NULL)`。注意硬链接不能跨卷，如果还原目标跨卷了要降级成复制并 warn。

### 6.3 元数据支持

#### 属性位

`GetFileAttributesW` / `SetFileAttributesW`。存整个 `DWORD`，但还原时要**屏蔽掉不可设置的位**：

```cpp
constexpr DWORD kSettableAttrs =
    FILE_ATTRIBUTE_READONLY | FILE_ATTRIBUTE_HIDDEN | FILE_ATTRIBUTE_SYSTEM |
    FILE_ATTRIBUTE_ARCHIVE  | FILE_ATTRIBUTE_TEMPORARY | FILE_ATTRIBUTE_OFFLINE |
    FILE_ATTRIBUTE_NOT_CONTENT_INDEXED;
```

`FILE_ATTRIBUTE_DIRECTORY`、`REPARSE_POINT`、`COMPRESSED`、`ENCRYPTED`、`SPARSE_FILE` 这些是文件系统维护的，硬塞会返回 `ERROR_INVALID_PARAMETER`。这也是个容易踩的坑。

#### 时间戳

`GetFileTime` / `SetFileTime`，三个 `FILETIME` 原样存。目录也要设——打开目录句柄需要 `FILE_FLAG_BACKUP_SEMANTICS`。

`SetFileTime` 要求句柄有 `FILE_WRITE_ATTRIBUTES` 权限。

**测试用例注意**：`lastAccessTime` 在 Windows 上默认可能被系统禁用更新（`NtfsDisableLastAccessUpdate` 注册表项），所以断言访问时间一致时要允许一定容差，或者在测试文档里说明这个平台行为。

#### 属主与权限（这一项的核心）

读：

```cpp
PSECURITY_DESCRIPTOR psd = nullptr;
GetNamedSecurityInfoW(path, SE_FILE_OBJECT,
    OWNER_SECURITY_INFORMATION | GROUP_SECURITY_INFORMATION | DACL_SECURITY_INFORMATION,
    nullptr, nullptr, nullptr, nullptr, &psd);

LPWSTR sddl = nullptr;
ConvertSecurityDescriptorToStringSecurityDescriptorW(
    psd, SDDL_REVISION_1,
    OWNER_SECURITY_INFORMATION | GROUP_SECURITY_INFORMATION | DACL_SECURITY_INFORMATION,
    &sddl, nullptr);
// sddl 形如 "O:S-1-5-21-...G:S-1-5-21-...D:AI(A;;FA;;;SY)(A;;FA;;;BA)..."
```

写：反向调用 `ConvertStringSecurityDescriptorToSecurityDescriptorW` + `SetNamedSecurityInfoW`。

**三个必须处理的现实问题**（写进设计文档，答辩时是深度体现）：

1. **设置属主需要 `SeRestorePrivilege`。** 普通用户只能把属主设成自己或自己所属的组。没有特权时：跳过 OWNER 部分，只还原 DACL，发 warn。
2. **SID 跨机器无意义。** `S-1-5-21-<机器/域标识>-1001` 这个用户在另一台机器上不存在。还原到异机时这些 ACE 会变成"无法解析的账户"。方案：还原时提供 `--sid-map` 可选参数做 SID 映射，默认行为是原样写入并对无法解析的 SID 发 warn。**这个不是 bug，是所有备份软件的固有问题**，写清楚比假装不存在好。
3. **继承标志。** SDDL 里的 `AI` 表示 DACL 是自动继承的。还原时如果父目录 ACL 不同，直接写一份带 `AI` 的 DACL 可能和继承来的冲突。稳妥做法：调 `SetNamedSecurityInfoW` 时用 `PROTECTED_DACL_SECURITY_INFORMATION` 显式控制是否阻断继承，依据存下来的 `SE_DACL_PROTECTED` 控制位。

**SACL（审计）不做**——需要 `SeSecurityPrivilege`，且和评分项无关。文档里说明为什么不做。
